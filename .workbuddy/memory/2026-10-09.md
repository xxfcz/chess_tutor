## 修复 pnpm dev 下 HMR WebSocket 连接失败

- 现象：`WebSocket connection to 'ws://198.18.0.1:3050/_next/hmr?id=...' failed`
- 根因：Next.js 16.4.0 的 `blockCrossSiteDEV` 只放行 `localhost` / `**.localhost` / 启动 hostname，
  其余 origin 访问 `/_next/*`（含 HMR WebSocket）直接 403。
  `198.18.0.1` 是本机 Mihomo/Clash Meta TUN 虚拟网卡地址，Next dev 把它当成 "Network" 地址打印，
  用户点该地址打开页面时 origin 不匹配 → HMR 被拦截。
- 定位方式：curl 模拟 WS 握手对比 Origin（localhost 返回 101，198.18.0.1 被断开）。
- 修复：在 `next.config.ts` 顶层新增 `allowedDevOrigins: ['198.18.0.1', '192.168.*.*', '10.*.*.*', '172.16.*.*']`。
  改完 dev server 会自动重载配置，已验证 198.18.0.1 源握手返回 101。
- 备注：本机项目实际安装的是 next 16.4.0（package.json 写 ^16.0.7）。
- 备选方案：直接用 http://localhost:3050 或 http://127.0.0.1:3050 访问即可绕开。

## 新增「测试连接」按钮（校验第三方 URL + API Key）

- 需求：配置第三方 AI 服务时能一键测试 URL 和 API Key 是否有效。
- 难点与设计取舍：本应用**真实调用是从浏览器直连** provider，所以浏览器直连探测才是最忠实的测试方式；
  但浏览器直连失败时无法区分「URL 打错/密钥无效」与「被 CORS 拦截」（都表现为 `Failed to fetch`）。
  解法：**两段式探测**——先用浏览器直连；若失败在网络层（非 HTTP 状态码），再走自家服务端代理
  `POST /api/v1/llm/test` 重试一次（服务端不受 CORS 约束），据此判定：
  - 直连成功 → `ok`
  - 直连返回 HTTP 错误 → 直接分类，不再重试（401/403→auth，404→model，429→quota，其他→error）
  - 直连网络失败 + 代理成功 → `cors`（**密钥有效，但浏览器被封，真实调用也会失败**）
  - 直连网络失败 + 代理返回 HTTP 错误 → 按代理结果分类（说明是真凭证问题）
  - 两者都网络失败 → `network`（URL 或网络不通）
- 新增文件：
  - `src/lib/llmConnectionTest.ts`：`testLLMConnection()`，返回 `{ok, outcome, message, detail, latencyMs, viaProxy}`；
    payload 用 `max_tokens: 1` 把测试成本压到近乎为零；`AbortController` 20s 超时。
  - `src/app/api/v1/llm/test/route.ts`：服务端探测代理（runtime=nodejs），返回 `{kind, status, detail}`。
    **注意它始终回 HTTP 200**，把真实错误放在 body 里，避免 4xx 被客户端当成代理自身失败。
  - `src/components/LLMConnectionTest.tsx`：可复用 UI 组件（按钮 + loading + 结果卡片，
    结果卡片按 `data-outcome` 区分绿/黄/红三态，并显示 `<pre>` 技术细节）。
    已从 `src/lib/llm.ts` 导出 `buildEndpoint` 供复用，避免两处 URL 拼接逻辑漂移。
- 接入位置：设置页「API Provider Configuration」区（Model 输入框下方）与 onboarding 第4步（Model 下方），
  共用一个组件，通过 props 传 `{baseUrl, apiKey, model, language}`。
