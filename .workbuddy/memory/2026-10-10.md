## 选型分析：chess_tutor 小程序化 vs 继续「黑白格大师」

- 用户诉求：总结 chess_tutor 功能特点，与他自研的微信小程序「黑白格大师」比较，判断是继续小程序还是把 chess_tutor 改成小程序二开。
- 用户补充的前提（AskUserQuestion 得到）：黑白格大师 = 原生小程序 + 云开发；核心（棋盘/走子/对战）已跑通，缺深度功能；目标商业变现；未正式上线，没有必须保留的资产。
- 产出：`docs/黑白格大师_vs_chess_tutor_选型分析.md`（完整报告）。
- 结论：**推荐继续黑白格大师，chess_tutor 只当参考实现，不当代码基座**。
  1. 授权硬伤：项目 GPL-3.0，`LICENSING.md` 明确第三方不得做专有移动端、不得移除 GPL，与闭源商业变现冲突。
  2. 可移植代码仅约 7%：全项目 ~2.5 万行，零 DOM 依赖的纯逻辑（`tacticDetection.ts` 383 + `tacticalLibrary.ts` 824 + `openings.ts` 226 + `personalities.ts` 268 + 提示词类 ~600）约 1900 行；UI 层（React 19 + react-chessboard + ChessGame.tsx 1031 行 / Tutor.tsx 1112 行）全废。
  3. 用户已跑通的棋盘/走子/对战，恰是 chess_tutor 里最难搬的部分的反面。

- 本次查证的关键事实（写报告时用到了，后续讨论可复用）：
  - 运行时战术题库**只有 31 题**：`src/lib/tacticalLibrary.ts` 直接 `import ../../fixtures/tactics/*.json`（每类 3–4 题，overloading 仅 3 题）。README 宣称的「Lichess 20+ per pattern」需先跑 `python3 scripts/setup_tactical_puzzles.py` 或 docker 启动脚本下载并覆盖写回 fixture，默认不生效。
  - `public/wikipedia/` 为空（仅 .gitkeep），维基开局背景需 `npm run cache:wikipedia`；服务端 GEMINI_API_KEY 未配 → `/api/v1/llm/opening-explanation` 恒走兜底。
  - `public/openings/` 8.6MB（moveIndex.json 4.6MB，12,379 条 ECO）；`public/stockfish/` 2.2MB WASM —— 均超小程序主包 2MB 限制，必须服务端化。
  - 全项目 `localStorage` 引用 138 处，`window./document.` 16 处。
  - 引擎有 `LocalEngine`（WASM，GPL）/ `RemoteEngine`（API）双实现，移动端构建剥离 Stockfish —— 小程序只能走 RemoteEngine。
  - 规模：src 下 114 个 ts/tsx、约 25,384 行；23 个测试文件 / 233 个 jest 用例；7 语言 i18n（translations.ts 1907 行）。

- 给出的落地建议（4 步，每步可独立上线）：① AI 讲解（云托管做 LLM 中转）② Stockfish 评估服务 ③ 战术识别**自己重写**（对照产品行为而非抄代码，规避 GPL 衍生作品风险）④ 开局库用公开数据源自建。
- 额外提醒：国内国际象棋 C 端付费天花板低，建议考虑少儿培训 B 端；合规上 AI 类目与主体资质需提前确认。
